# Durable Product and Architecture Decisions

Record decisions that future sessions should not casually reopen. If a decision is superseded, mark it superseded instead of deleting its history.

## D001 — Product identity

**Status:** Active
**Decision:** The product is an AI Executive Coach Command Center, not a certification app.
**Reason:** The user needs one operating system for multiple projects, priorities, execution, review, and AI operations. Learning is one capability within that system.
**Consequence:** Primary branding and navigation must be executive/workflow oriented while preserving the learning module.

## D002 — Learning remains protected

**Status:** Active
**Decision:** Existing curriculum, notes, captures, practice, flashcards, review behavior, persistence, Academy behavior, and working IPC contracts are compatibility boundaries.
**Reason:** Product repositioning must not destroy valuable work or data.
**Consequence:** New command-center features are additive and must not silently migrate or rename learning data.

## D003 — Local-first default

**Status:** Active
**Decision:** Keep the application local-first unless a future phase explicitly approves a backend, sync, or external integration.
## D004 — Credential boundary

**Status:** Active

**Decision:** Never expose credentials, cookies, passwords, authorization headers, or secrets to the renderer, logs, documents, commits, diagnostics, or provider-facing model context. Explicitly approved provider credentials may be stored only in the Electron main process using OS-backed encryption and may be used only for the approved provider request.

**Reason:** Provider integrations require a secure boundary, while the renderer and project artifacts must remain credential-free.

**Consequence:** Credential-bearing integrations require explicit approval, safe-storage availability, redacted status/diagnostics, and a documented removal path. Academy credentials and session secrets remain prohibited.

## D005 — Coach permissions

**Status:** Active design constraint
**Decision:** The coach may eventually read structured app state and draft recommendations, but data mutations require user approval, are explainable, and must be reversible.
**Reason:** Executive support should increase agency, not create hidden automation.
**Consequence:** Do not build unrestricted autonomous write access.

## D006 — Usage data must be real and attributable

**Status:** Active
**Decision:** The first usage ledger should track requests generated by this app when real provider response metadata is available.
**Reason:** Provider-wide usage cannot be claimed without a verified source.
**Consequence:** Every usage view must identify its source, scope, and limitations; no fake values.

## D007 — ADHD-aware

**Status:** Active
**Decision:** Use practical executive-function support patterns such as concrete next actions, reduced overload, focus limits, and visible blockers.
**Reason:** The product should be helpful and safe.
**Consequence:** UX copy and coach prompts must avoid clinical promises.

## D008 — One bounded phase at a time

**Status:** Active
**Decision:** Every session works on one bounded objective; every phase has explicit non-goals, acceptance criteria, verification, and a stop condition.
**Reason:** The product vision is intentionally broad and otherwise will produce disconnected half-built systems.
**Consequence:** Future sessions must not begin later-phase work without explicit approval.

## D009 — Documentation authority

**Status:** Active
**Decision:** Resolve conflicts using: current user instruction, `PROJECT_BRIEF.md`, this file, active phase plan, `PRODUCT_VISION.md`, `PROJECT_STATUS.md`, then older transcripts.
**Reason:** Current scope must override stale historical plans.
**Consequence:** Update the authoritative document when requirements change.

## D010 — Phase 1 shell boundary

**Status:** Superseded by D011
**Decision:** Phase 1 established only the Executive Coach Command Center product shell and information architecture around the existing Learning & Development module.
**Reason:** The broader product direction needed a truthful identity and navigation foundation before new workflow systems were introduced.
**Consequence:** The shell may show existing learning-derived state and clearly labeled planned areas, but must not fabricate projects, tasks, coaching, metrics, integrations, or provider data.

## D011 — Kanban board is the top implementation priority

**Status:** Historical sequencing constraint; superseded for current execution by D014
**Decision:** The local Projects + Tasks + Kanban workflow was the highest-priority implementation area before Today’s Focus. Its runtime acceptance established the structured roadmap foundation required by the current phase.
**Reason:** A reliable visual board is the first concrete operating workflow in the command center and provides the foundation for later prioritization and coaching.
**Consequence:** The board remains the complete work inventory and its compatibility boundaries remain protected. The active execution boundary is now `AICC-PHA-023` and its feature roadmap; do not use this historical decision to defer Today’s Focus or grounded coach implementation.

## D012 — Board state is designed for a future North Star/OR document layer

**Status:** Active future-facing constraint
**Decision:** Keep Projects + Tasks + Kanban records structured, stable-ID based, local-first, and attributable so a future North Star AI layer can read the board together with OR documents and produce explainable recommendations without hidden mutation.
**Reason:** The user wants North Star to eventually work from the board in conjunction with OR documents. The board should therefore be a trustworthy source of structured work state, not a presentation-only mockup.
**Consequence:** Do not add AI automation, document ingestion, cloud sync, credentials, or autonomous writes in the current Kanban phase. Future integrations must use explicit document provenance, read-only context by default, user approval for mutations, and reversible changes.

## D013 — Today View is a derived, read-only window over roadmap records

**Status:** Superseded by D014 for phase `AICC-PHA-023`
**Decision:** The historical Today View was always *derived* from the persisted roadmap; it never stored a second copy of task state and it never mutated tasks. Its original blocked-first ordering is retained here as historical context only.
**Reason:** The earlier contract predated dependency-aware Focus and incorrectly treated blocked work as a primary action. It remains useful as the compatibility history for `AICC-TSK-001`–`003`, but must not govern Today’s Focus.
**Consequence:** Implementations must use D014 for the current Focus/Waiting behavior. Do not restore blocked-first behavior.

## D014 — Today’s Focus includes grounded coaching within a validated boundary

**Status:** Active (Release 1, phase `AICC-PHA-023`)
**Decision:** Today’s Focus is a derived, dependency-aware action surface over the canonical local roadmap. It shows no more than three ready tasks, keeps blocked and dependency-waiting work separate, and treats a dependency as complete only when its referenced task is `done`. The grounded AI Executive ADHD Coach is a required part of this feature, not future compatibility work. It may recommend one realistic next action only from the validated Focus/Waiting snapshot, must explain its reason and uncertainty, must support deterministic fallback, and must receive explicit user approval before any supported mutation.
**Reason:** A deterministic queue without grounded coaching does not deliver the intended ADHD-oriented reduction from overwhelm to one actionable next step. Keeping the deterministic derivation authoritative prevents the provider from deciding what is possible or inventing work.
**Consequence:** Provider responses require schema and current-roadmap validation. Unknown, stale, blocked, dependency-locked, completed, archived, or out-of-context recommendations are rejected. The coach may not create, delete, complete, reprioritize, or rewire work autonomously; approved changes use the existing validated update path. Credentials remain outside renderer state, roadmap data, and recommendation records. App-originated usage and compact recommendation metadata may be recorded locally with explicit privacy controls; provider-wide usage must not be implied.

## D015 — Current coach implementation is a validated, display-only slice

**Status:** Active implementation state (2026-08-08)

**Decision:** The current Ask AI Coach integration sends only the bounded Focus/Waiting context and requests a strict JSON recommendation. The renderer validates the returned task ID, action, explanation, uncertainty, and readiness against the current Focus snapshot before displaying it. Plain-text, malformed, unknown, blocked, dependency-locked, completed, and out-of-context recommendations are rejected. Displaying or reviewing a recommendation never mutates roadmap data.

**Reason:** This is the smallest safe implementation slice that makes provider output grounded without allowing the provider to decide readiness or write to the roadmap.

**Consequence:** This decision defines the grounded, display-only coach boundary for the MVP. Deferred fallback, provenance/freshness, privacy, usage, approval/audit, expanded testing, and manual acceptance work remain post-MVP scope. It does not authorize autonomous writes or imply provider-wide usage reporting.

## D016 — Ship the AI coach happy path before deferred hardening

**Status:** Active MVP scope (2026-08-08)

**Decision:** The initial MVP is the user-triggered happy path: build bounded Focus context, call OpenRouter through the Electron main process, parse one structured recommendation, validate its task against the current Focus list, display the recommendation, and let the user open the task in Projects. Privacy controls, fallback behavior, freshness/provenance, usage tracking, approval mutations, audit records, and exhaustive Electron acceptance are deferred post-MVP.

**Reason:** The immediate product goal is to demonstrate the core coaching loop without expanding the first delivery into a complete production-hardening program.

**Consequence:** The MVP requires `OPENROUTER_API_KEY` and network access. Basic task grounding validation remains in place so the provider cannot recommend work outside the current Focus list. Deferred scope must not be represented as implemented or silently treated as production readiness.

## D017 — AI may propose only a user-approved next-action update

**Status:** Active MVP scope (2026-08-08)

**Decision:** A validated AI recommendation may offer one proposed `nextAction`. The user may open the task, dismiss the recommendation, or review a confirmation preview showing the current and proposed values. Only explicit Apply calls the existing validated task-update IPC path, and Apply rechecks that the task remains in the current Focus list. No completion, deletion, dependency, priority, or autonomous mutation is supported.

**Reason:** The first useful action is to turn a recommendation into a concrete next action while preserving an explicit approval boundary.

**Consequence:** Successful application refreshes Today’s Focus and reports the update. Failed or no-longer-current proposals are not applied and remain visible as errors for user review.
